PHASE 1 — AUTHENTICATION & FIRST TABLES (User + RefreshToken)
================================================================

DATE: 2026-08-31
PHASE: 1.2 — First real business tables (ADR-016)
OBJECTIVE:
  Introduce the first business tables — `users` and `refresh_tokens` — to back
  the Phase 1 JWT authentication (ADR-015): stateless Bearer access token +
  refresh token persisted in DB (sha256-hashed, rotated & revocable). Governed
  by ADR-016 (auth tables) and ADR-015 (auth architecture).

DATABASE ACTIONS:
  - Created Prisma models `User` and `RefreshToken` in
    apps/api/prisma/schema.prisma:
      * enum `Role` (ADMIN | USER)
      * `users`: id (cuid PK), email (unique), passwordHash, name?, role
        (default USER), isActive (default true), createdAt, updatedAt.
      * `refresh_tokens`: id (cuid PK), tokenHash (unique), userId (FK -> users,
        onDelete: Cascade), expiresAt, revokedAt?, createdAt.
  - Migration applied on the local dev DB. Created Prisma migration baseline
    `_prisma_migrations` AND the `users` + `refresh_tokens` tables.

MIGRATIONS:
  - Migration folder: apps/api/prisma/migrations/20260830053420_init_auth/
  - Name: `init_auth`. Applied via
    `corepack pnpm --filter @icode-host-pro/api run migrate --name init_auth`.
    NOTE: avoid passing the literal `--`; use the `--name init_auth` form so the
    CLI does not drop into an interactive name prompt (hung when run with `--`).
  - First migration on the project => created `_prisma_migrations` tracking
    table (Phase 0 had none, per ADR-014). Confirmed: `prisma migrate status`
    reports DB is in sync.
  - Troubleshooting note: a stale pg advisory lock (P1002) can block `migrate
    dev` after a killed migration; cleared with `docker compose restart postgres`
    (drops all in-flight advisory locks) then re-ran the migration.

IMPORTANT SQL / COMMANDS:
  - Migration (dev):  corepack pnpm --filter @icode-host-pro/api run migrate --name <name>
  - Deployment:       corepack pnpm --filter @icode-host-pro/api run migrate:deploy
  - The two tables created (mirror of Prisma schema; quoted names as generated
    by Prisma):

    CREATE TYPE "Role" AS ENUM ('ADMIN', 'USER');
    ,
    CREATE TABLE "users" (
        "id"          TEXT NOT NULL,
        "email"       TEXT NOT NULL,
        "passwordHash" TEXT NOT NULL,
        "name"        TEXT,
        "role"        "Role" NOT NULL DEFAULT 'USER',
        "isActive"    BOOLEAN NOT NULL DEFAULT true,
        "createdAt"   TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
        "updatedAt"   TIMESTAMP(3) NOT NULL,
        CONSTRAINT "users_pkey" PRIMARY KEY ("id")
    );
    CREATE UNIQUE INDEX "users_email_key" ON "users"("email");
    CREATE INDEX "users_email_idx" ON "users"("email");

    CREATE TABLE "refresh_tokens" (
        "id"          TEXT NOT NULL,
        "tokenHash"   TEXT NOT NULL,
        "userId"      TEXT NOT NULL,
        "expiresAt"   TIMESTAMP(3) NOT NULL,
        "revokedAt"   TIMESTAMP(3),
        "createdAt"   TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
        CONSTRAINT "refresh_tokens_pkey" PRIMARY KEY ("id")
    );
    CREATE UNIQUE INDEX "refresh_tokens_tokenHash_key" ON "refresh_tokens"("tokenHash");
    CREATE INDEX "refresh_tokens_userId_idx" ON "refresh_tokens"("userId");
    ALTER TABLE "refresh_tokens" ADD CONSTRAINT "refresh_tokens_userId_fkey"
        FOREIGN KEY ("userId") REFERENCES "users"("id") ON DELETE CASCADE ON UPDATE CASCADE;

VALIDATION QUERIES:
  - `SELECT id, email, role, "isActive" FROM users;`  -> rows returned after a
    register/login (each issue-time row for users).
  - `SELECT "tokenHash", "userId", "revokedAt", "expiresAt" FROM refresh_tokens;`
    -> one row per issued token; `revokedAt` becomes non-null after refresh
    rotation or logout.
  - Live e2e + smoke test proved writes/reads: register persisted a user row,
    refresh rotated (old token revoked, new one issued), logout revoked the
    presented token (subsequent refresh returned 401).
  - NOTE: token hashes are stored, never the raw refresh token (ADR-015 sha256).

RESULT:
  - First business tables `users` + `refresh_tokens` created with migration
    baseline. Auth flow fully backed by real tables (register/login/refresh/
    logout). No seed data inserted (not required in Phase 1).

ROLLBACK NOTES:
  - To revert this migration on dev (destructive, removes data):
        corepack pnpm --filter @icode-host-pro/api run migrate:deploy  # (not a rollback)
    A true rollback would require a down-migration; none authored. For dev a
    full reset is acceptable:
        docker compose down -v && docker compose up -d postgres
    which drops icode_pg_data + recreates the empty DB (re-run `migrate dev`
    afterwards to re-apply all migrations).

REMARKS FOR FUTURE AI:
  - All future domain tables follow this pattern: model in schema.prisma, then a
    named migration, recording the SQL here.
  - `refresh_tokens` stores only sha256 hashes — never raw tokens, secrets or
    session dumps.

PHASE 2 — CORE MODEL: Product + Server (platform-global reference entities)
================================================================

DATE: 2026-08-31
PHASE: 2.0/2.2 — Core domain tables (ADR-017)
OBJECTIVE:
  Introduce the two platform-GLOBAL reference entities `Product` (catalogue)
  and `Server` (infrastructure host), each possessed by the PLATFORM, NOT by a
  client. They carry NO ownerId. Client-owned resources (Subscription/Service/
  Deployment…) are deliberately deferred to future phases when a real workflow
  needs them. RBAC is ADMIN/USER via existing Role enum (ADR-015).

DATABASE ACTIONS:
  - Added enums `ProductStatus` (DRAFT/ACTIVE/SUSPENDED/DISABLED) and
    `ServerStatus` (UNKNOWN/PROVISIONING/ACTIVE/PROBLEM/REMOVED).
  - Added models `Product` and `Server` (no relation to User; global).
  - Migration applied locally on the dev DB (containers: icode-postgres,
    database icode_host_pro).

MIGRATIONS:
  - Migration folder: apps/api/prisma/migrations/20260831000649_init_core/
  - Name: `init_core`. Applied via
    `corepack pnpm --filter @icode-host-pro/api run migrate --name init_core`.
  - `prisma migrate dev` regenerated the Prisma Client (v6.19.3) automatically.

IMPORTANT SQL / COMMANDS:
  - The migration SQL (mirror of Prisma schema):

    CREATE TYPE "ProductStatus" AS ENUM ('DRAFT', 'ACTIVE', 'SUSPENDED', 'DISABLED');
    CREATE TYPE "ServerStatus"  AS ENUM ('UNKNOWN', 'PROVISIONING', 'ACTIVE', 'PROBLEM', 'REMOVED');

    CREATE TABLE "Product" (
        "id"        TEXT NOT NULL,
        "name"      TEXT NOT NULL,
        "kind"      TEXT NOT NULL DEFAULT 'generic',
        "status"    "ProductStatus" NOT NULL DEFAULT 'ACTIVE',

    CREATE TABLE "Server" (
        "id"        TEXT NOT NULL,
        "name"      TEXT NOT NULL,
        "hostname"  TEXT NOT NULL,
        "status"    "ServerStatus" NOT NULL DEFAULT 'UNKNOWN',
        "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
        "updatedAt" TIMESTAMP(3) NOT NULL,
        CONSTRAINT "Server_pkey" PRIMARY KEY ("id")
    );
    CREATE UNIQUE INDEX "Server_name_key" ON "Server"("name");

  - Run migrations (dev):  corepack pnpm --filter @icode-host-pro/api run migrate --name <name>

VALIDATION QUERIES:
  - `SELECT id, name, kind, status FROM "Product";`   -> catalogue rows.
  - `SELECT id, name, hostname, status FROM "Server";` -> infra rows.
  - `SELECT id, email, role FROM "User" WHERE role='ADMIN';` -> the seeded admin.

RESULT:
  - `Product` + `Server` tables created (platform-global, no ownerId). RBAC
    enforced at API level (Product read = any authenticated; Product mutation &
    all Server routes = ADMIN). Verified live: USER can GET /products (200) but
    POST /products and GET/POST /servers are 403; unauthenticated is 401.

ROLLBACK NOTES:
  - A down-migration is not authored. To drop these tables on dev (destructive):
        corepack pnpm --filter @icode-host-pro/api run migrate:deploy  # no-op
    A full dev reset drops everything instead:
        docker compose down -v && docker compose up -d postgres
    then re-run `migrate dev` to re-apply all migrations (init_auth, init_core).

REMARKS FOR FUTURE AI:
  - Product/Server are reference data for the PLATFORM. Do NOT later add ownerId
    or a User relation to them for "client ownership": a client's relationship
    to a product/server belongs to FUTURE client-owned entities (Subscription/
    Service/Deployment), to be introduced only when a real workflow needs them.
  - `Product.kind` is a String (not an enum) by design — the product-kind list

PHASE 5 — ESPACE CLIENT + ACCÈS SÉCURISÉ (ADR-020 invitations, ADR-021 client)
================================================================

DATE: 2026-08-31
PHASE: 5.1 — Client access model: Invitation + Subscription + Service
OBJECTIVE:
  Close public registration (ADR-020): new USER accounts are created only via an
  ADMIN-issued invitation (raw token shown once, sha256 stored). Then the first
  CLIENT-OWNED workflow (ADR-021): a USER subscribes to a platform Product; after
  ADMIN approval the client requests a Service; the ADMIN assigns a hosting Server
  and (STUB) advances status. The client never touches infrastructure (no Server
  data in client payloads). One migration `init_client_access` adds all three
  tables + 2 enums.

DATABASE ACTIONS:
  - Created enums `SubscriptionStatus`
    (PENDING/ACTIVE/REJECTED/SUSPENDED/CANCELLED) and `ServiceStatus`
    (REQUESTED/PROVISIONING/ACTIVE/PROBLEM/SUSPENDED/REMOVED) in
    apps/api/prisma/schema.prisma.
  - Created models:
    * `Invitation` — email, `tokenHash` (sha256 of raw one-time token, @unique;
      raw never persisted), `issuerId` (nullable FK -> User, onDelete SetNull —
      a deleted admin's pending invites survive), `expiresAt`, `usedAt?`,
      `revokedAt?`, createdAt; @@index([email]).
    * `Subscription` — `userId` (FK -> User, onDelete Cascade), `productId`
      (FK -> Product, onDelete Restrict), `status` default PENDING, timestamps;
      @@index([userId]), @@index([status]).
    * `Service` — `name`, `subscriptionId` (FK -> Subscription, onDelete
      Cascade), `serverId` (nullable FK -> Server, onDelete SetNull — a service
      can exist unassigned), `status` default REQUESTED, timestamps;
      @@index([subscriptionId]).
  - Added back-relations: `User.subscriptions` + `User.issuedInvites`,
    `Product.subscriptions`, `Server.services`.
  - Migration applied locally (containers icode-postgres, db icode_host_pro).
    `Deployment` stays deferred.

MIGRATIONS:
  - Migration folder: apps/api/prisma/migrations/20260831084839_init_client_access/
  - Name: `init_client_access`. Applied via
    `corepack pnpm --filter @icode-host-pro/api run migrate --name init_client_access`.
  - `prisma migrate status` -> up to date, 4 migrations total (init_auth, init_core,
    init_audit, init_client_access). Prisma Client regenerated v6.19.3.

IMPORTANT SQL / COMMANDS:
  - The migration SQL (mirror of Prisma schema; note ALL Prisma table names are
    quoted in Postgres, e.g. "Subscription"):

    CREATE TYPE "SubscriptionStatus" AS ENUM ('PENDING', 'ACTIVE', 'REJECTED', 'SUSPENDED', 'CANCELLED');
    CREATE TYPE "ServiceStatus" AS ENUM ('REQUESTED', 'PROVISIONING', 'ACTIVE', 'PROBLEM', 'SUSPENDED', 'REMOVED');

    CREATE TABLE "Invitation" (
        "id"        TEXT NOT NULL,
        "email"     TEXT NOT NULL,
        "tokenHash" TEXT NOT NULL,
        "issuerId"  TEXT,
        "expiresAt" TIMESTAMP(3) NOT NULL,
        "usedAt"    TIMESTAMP(3),
        "revokedAt" TIMESTAMP(3),
        "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
        CONSTRAINT "Invitation_pkey" PRIMARY KEY ("id")
    );
    CREATE UNIQUE INDEX "Invitation_tokenHash_key" ON "Invitation"("tokenHash");
    CREATE INDEX "Invitation_email_idx" ON "Invitation"("email");
    ALTER TABLE "Invitation" ADD CONSTRAINT "Invitation_issuerId_fkey"
        FOREIGN KEY ("issuerId") REFERENCES "users"("id") ON DELETE SET NULL ON UPDATE CASCADE;

    CREATE TABLE "Subscription" (
        "id"        TEXT NOT NULL,
        "userId"    TEXT NOT NULL,
        "productId" TEXT NOT NULL,
        "status"    "SubscriptionStatus" NOT NULL DEFAULT 'PENDING',
        "createdAt" TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
        "updatedAt" TIMESTAMP(3) NOT NULL,
        CONSTRAINT "Subscription_pkey" PRIMARY KEY ("id")
    );
    CREATE INDEX "Subscription_userId_idx"   ON "Subscription"("userId");
    CREATE INDEX "Subscription_status_idx"   ON "Subscription"("status");
    ALTER TABLE "Subscription" ADD CONSTRAINT "Subscription_userId_fkey"
        FOREIGN KEY ("userId") REFERENCES "users"("id") ON DELETE CASCADE ON UPDATE CASCADE;
    ALTER TABLE "Subscription" ADD CONSTRAINT "Subscription_productId_fkey"
        FOREIGN KEY ("productId") REFERENCES "Product"("id") ON DELETE RESTRICT ON UPDATE CASCADE;

    CREATE TABLE "Service" (
        "id"             TEXT NOT NULL,
        "name"           TEXT NOT NULL,
        "subscriptionId" TEXT NOT NULL,
        "serverId"       TEXT,
        "status"         "ServiceStatus" NOT NULL DEFAULT 'REQUESTED',
        "createdAt"      TIMESTAMP(3) NOT NULL DEFAULT CURRENT_TIMESTAMP,
        "updatedAt"      TIMESTAMP(3) NOT NULL,
        CONSTRAINT "Service_pkey" PRIMARY KEY ("id")
    );
    CREATE INDEX "Service_subscriptionId_idx" ON "Service"("subscriptionId");
    ALTER TABLE "Service" ADD CONSTRAINT "Service_subscriptionId_fkey"
        FOREIGN KEY ("subscriptionId") REFERENCES "Subscription"("id") ON DELETE CASCADE ON UPDATE CASCADE;
    ALTER TABLE "Service" ADD CONSTRAINT "Service_serverId_fkey"
        FOREIGN KEY ("serverId") REFERENCES "Server"("id") ON DELETE SET NULL ON UPDATE CASCADE;

  - Env (optional): `INVITE_EXPIRES_IN_DAYS=7` (default 7) in apps/api/.env(.example).
  - Endpoints added Phase 5:
      PUBLIC:  POST /api/auth/accept-invite            (register -> 410 Gone)
      ADMIN:   GET/POST /api/invitations ; POST /api/invitations/:id/revoke
      CLIENT(any auth): GET/POST /api/client/subscriptions ;
                 PATCH /api/client/subscriptions/:id/cancel ;
                 GET/POST /api/client/services
      ADMIN:   GET /api/admin/subscriptions ;
                 PATCH /api/admin/subscriptions/:id {status}
               GET /api/admin/services ;
                 PATCH /api/admin/services/:id {status?, serverId?}

VALIDATION QUERIES:
  - Invitations lifecycle:
      SELECT id, email, "tokenHash", "expiresAt", "usedAt", "revokedAt" FROM "Invitation" ORDER BY "createdAt" DESC;
  - Client workspace (join the ownership chain):
      SELECT s.id, s.status AS sub_status, u.email, p.name AS product,
             sv.id AS service_id, sv.status AS service_status, sv."serverId",
             srv.name AS server
      FROM "Subscription" s
      JOIN "User" u    ON u.id = s."userId"
      JOIN "Product" p ON p.id = s."productId"
      LEFT JOIN "Service" sv ON sv."subscriptionId" = s.id
      LEFT JOIN "Server" srv ON srv.id = sv."serverId"
      ORDER BY s."createdAt" DESC;
  - Register is closed: `POST /api/auth/register` (live) -> 410 Gone. A fresh
    account can only exist through accept-invite.

RESULT:
  - All three Phase 5 tables live (4 migrations total, up to date). Verifié en
    e2e (51/51, 7 suites) et build API+web PASS sur Postgres réel. Live smoke:
    /api/health ok; register -> 410; login admin -> token; GET /api/products 200;
    GET /api/invitations (ADMIN) 200.
